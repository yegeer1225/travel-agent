# 评测集录入指南（fixtures）

这里放**人工筛过的真实攻略原文**（10~20 篇起步，先攒成都的）。
评测运行器只读 `eval/cases/*.json`；fixtures 是**原文素材**，
case 从这里生成（原文 + 你标注的已知错误）。

> ⚠️ **单向同源（A38）**：`fixtures → 产品`（可当攻略库种子数据），
> **永不回读**——线上用户发的攻略不自动进评测集。

## 攻略怎么攒（技术方案.md 第 8 节的原始任务）

1. 浏览器打开马蜂窝游记 / 知乎 / 公众号里的**含具体行程的攻略**
   （要有 Day1/Day2…、交通方式、时间）
2. 全文复制存成 `.md`，文件名 = `来源-城市-标题缩写.md`（如 `mafengwo-chengdu-2d.md`）
3. 每篇记一笔你知道的**问题**（下一节讲什么能标）

## 什么错能标进评测（风险 11 的纪律）

**只标硬判据能验证的错** —— 判分零 LLM，标了判不了的都是白标。

⚠️ **更要紧的一条（2026-09-17 读代码实测）**：`should_flag` 只有 hotstart 用，
而 hotstart 走 `paste.py`，它有两条约束会**让某些判据永远出不来**：

| 判据 | hotstart 能触发吗 | 为什么 |
|---|---|---|
| `walk_load` | ✅ **唯一稳的** | 站数 × 1.2km，纯站数决定，不依赖外部数据 |
| `open_today` | ⚠️ 能，但要设计 | 该 POI 得有 `open_time`；且**到达时刻是代码顺推的**（见下） |
| `reachable` | ⚠️ mock 单跳不能、**累计能** | mock 池内最大单跳 **88min**（太古里↔都江堰），够不到 120；但**当天累计能**（武侯祠→都江堰→青城山→熊猫基地 = 85+43+85 = 213 > 180） |
| `poi_exists` | ❌ **永远不能** | 搜不到的地名走 `skipped`，**根本不进 `Trip.stops`** → 恒为 pass |
| `weather_conflict` | ❌ **永远不能** | `paste.py` 硬写 `Weather(UNAVAILABLE)` → 恒为 unknown |
| `max_days` / `min_stops` | ❌（不属于 should_flag） | 是结构断言，给 coldstart 用 |

**所以能标进 `should_flag` 的 code 只有三个：`walk_load` / `open_today` / `reachable`。**

### 触发线（`validate.py` 里读出的真阈值）

`day_stats.walk_km = 当天解析成功站数 × 1.2`（**估算，不是实测** —— 高德没有步行距离数据）

| 同行人 | 步行上限 | 触发所需站数 | 边界（不触发） |
|---|---|---|---|
| 无 | 8.0 km | **≥7 站**（7×1.2=8.4） | 6 站 = 7.2 绿 |
| 有长辈 | 5.0 km | **≥5 站**（5×1.2=6.0） | 4 站 = 4.8 绿 |
| 有小孩（无长辈） | 6.0 km | **≥6 站**（6×1.2=7.2） | **5 站 = 6.0 绿** ← 最刁的边界（`<=` 判通过） |

`reachable`：单跳 >120 min（有长辈 >90）｜当天累计 >180 min（有长辈 >150）

⚠️ **档位由粘贴文本里的词决定**（"带爸妈/父母/老人" → `elders`；"带小孩/孩子" → `children`；
没提 = `null` = 默认档）。同一份行程**加一句「带着爸妈」就能从绿翻红** ——
这是分档的意义，也是最好用的一种埋点（只需改一句话，不改站点）。

### 五种已验证可触发的埋法（2026-09-17 实测，对应 `eval/cases/web-chengdu-*.json`）

| 判据 | 埋法 | 实测结果 | 脆弱度 |
|---|---|---|---|
| `walk_load` | ① 原文**加一句「带着爸妈」** | 同一份五站行程：不带长辈 6.0≤8.0 **绿** → 带长辈 6.0>5.0 **红** | 低（一句话） |
| `walk_load` | ② 同篇**加减一个站** | 带娃档：5 站=6.0 **绿**（边界）／6 站=7.2 **红** | 低（纯算数） |
| `open_today` | ③ 把开门晚的 POI 排到**当天第 1 站** | 太古里（10:00-22:00）排第 1 → 到达恒为 09:00 → **红** | **零** —— 09:00 是常量，不依赖距离/停留 |
| `open_today` | ④ 把早关门的 POI 排到**足够靠后** | 熊猫基地（07:30-17:00）排第 6 站 → 顺推 17:41 → **红** | 中（依赖默认停留 90 与车程） |
| `reachable` | ⑤ 一天塞**远郊三连**（都江堰 + 青城山） | 累计 213 > 180 → **红**（单跳最大 85，都不到 120） | 中（依赖池内有远郊点） |

**起步就用 ③** —— 它不依赖任何数字，是 `open_today` 最稳的埋法。

### 已形成的边界对台账（坑 3：每条阈值判据都要「界内绿 + 超一点红」）

| 阈值 | 界内绿 | 超一点红 |
|---|---|---|
| 步行 8.0 km（默认档） | `tianfu-clean`（5 站 = 6.0） | ⛔ **缺**（要 7 站，mock 池仅 9 点且搜不到的会被跳过） |
| 步行 5.0 km（长辈档） | `walkload-elder-green`（4 站 = 4.8） | `tianfu-elders`（5 站 = 6.0） |
| 步行 6.0 km（小孩档） | `3d-family-green`（5 站 = 6.0，恰好 `<=`） | `3d-family-red`（6 站 = 7.2） |
| 单跳 90 min（长辈档） | `reachable-elder-green`（85 min，**6 分钟余量**） | ⛔ 缺（real-only） |
| 单跳 120 min | ⛔ 缺（real-only） | `reachable-single-hop`（~150 min，real-only） |
| 当天累计 180 min | ⛔ 缺 | `reachable-day-total`（213 min） |
| `open_today` 时段 | `reachable-elder-green`（都江堰 11:55 落在 08:00-18:00 内） | `open-too-early`（09:00 < 10:00 开门）／`open-too-late`（17:41 > 17:00 闭园） |

`reachable-elder-green` 那条正例**有来历**：`mock.py` 的距离校准注释里记着，改造前 mock 把
「人民公园→都江堰」算成 160 min，于是带长辈上限 90 min 的判据**把一份正常行程判成硬错、
白打回两轮**。它就是那道伤疤的回归防线。

### 🔴 粘贴路径的到达时刻是代码算的，不是文本说的

`paste.py` 从 `DAY_START = "09:00"` 起，逐站 `arrive → + stay_min → + 车程` 顺推。
所以原文写「晚上 8 点去武侯祠」**对到达时刻毫无影响**。要埋 `open_today`，
只能靠**把早关门的点排到足够靠后**（前面堆站数 / 堆停留时长，把时间推过它的闭馆点）。

| 不能标 ❌ | 为什么 |
|---|---|
| "这个行程不合理" / "太赶了"（无数字） | 主观，硬判据不产生对应 fail |
| "门票写错了" | 门票数据大面积缺失，判不了（坑 4） |
| "这人少/人多" | 没有数据源 |
| "那天闭馆" | 高德 `open_time` 只有每天时段、**没有周几闭馆**；`open_today` 判的是"到达时刻在不在营业时段内" |

## 从攻略原文到 case

原文攒好后，每个 case 一个 JSON 放 `eval/cases/`（格式照着 `demo-*.json` 抄）：

```json
{
  "id": "mafengwo-chengdu-2d",
  "kind": "hotstart",
  "title": "马蜂窝某篇成都两日（含 2 处标注错误）",
  "source": "马蜂窝 <URL>",
  "text": "攻略原文的行程部分（Day1…Day2…，别整篇博客都贴进来）",
  "destination": "成都",
  "k": 3,
  "expect": {
    "should_flag": [
      { "code": "walk_load", "day": 2, "note": "原文带爸妈却排了 5 个点" }
    ],
    "must_contain_pois": ["武侯祠"]
  }
}
```

- `code` 只能取硬判据的：`walk_load` / `open_today` / `reachable`
  （⚠️ 当天车程超限的 code 也是 `reachable`，看 msg 区分；**`poi_exists` 在 hotstart 触发不了**，见上表）
- `k ≥ 3` 才有 pass^k 的意义（一致性）；k 越大越贵，DeepSeek 一次全流程约 0.3~0.5 元
- 冷启动 case（`kind: "coldstart"`）测的是**生成**：文本写一句话需求，
  `expect` 用 `max_days` / `min_stops`，不标 `should_flag`
- `requires`（可选）：把 case 绑到某个 provider，如 `"requires": "real"`。
  有些判据**物理上只在一个 provider 下可触发**（`reachable` 单跳：mock 池内最大单跳 88min）。
  不写 = 两个模式都跑；写了不匹配就**跳过**，并在 console 与报告头部列出被跳过的 id ——
  这样 mock 全量跑的"全绿基线"不会被 real-only 的 case 打红，
  也不用靠人记着该 `--cases` 排除哪几条（**靠记的约束必然腐烂**）

### `should_not_flag`：测误报的反向断言（2026-09-17 加）

`should_flag` 只能表达"**必须报**"。但**正例**（真攻略原样、本来就合理）和
**阈值边界例**（刚好卡在界内）要表达的是"**不该报**" —— 出 fail 就是**误报**。
误报是最贵的一项：冤枉一次会让 agent 白重排一轮（钱 + 时间）。

```json
"expect": {
  "should_flag":     [{ "code": "walk_load", "day": 2 }],
  "should_not_flag": [{ "code": "walk_load", "day": 1 }]
}
```

两者都支持 `day` 精确匹配（`day` 缺省 = 任意一天）；`status=unknown` **不算**误报
（三态，见 `方案.md` 6.2）。

### 边界：fixtures 只做评测素材

爬来的真攻略有版权，**只留在本目录当本地评测素材**：不进部署产物、
不进攻略库公开内容（社区内容走 M12 的「行程 → 攻略」链路自产）。
`fixtures → 产品`（A38）那条单向同源指的是**人工筛过、可用于播种的**素材，
不覆盖外部原创游记。
