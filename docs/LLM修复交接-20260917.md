# 后端 LLM 链路修复交接（2026-09-17）

> 本文档记录本次「旅游规划慢/不响应」排查结论与后端改动，供后续维护者（豆包 / 后端同学）交接。
> 改动人：前端侧协作排查后修改；所有改动可回滚（见第四节）。

---

## 一、现象与根因

**现象**：`/assistant` 发消息后永远只回「好的。还差两项必填项就能开始排…」，看起来像"没反应 / 卡住 / 慢"。

**根因（已实测确认）**：

1. `.env` 主链路（`LLM_MODEL_TOOL/PLAN=deepseek-flash`）走 **DeepSeek 付费 key（`LLM_API_KEY`）**，该 key **余额耗尽**。
   - 实测 `POST /sessions/{id}/chat` 的 SSE `error` 事件：
     ```
     APIStatusError: Error code: 402 - Insufficient Balance
     ```
2. `parse_intent`（需求抽取节点）每次 LLM 调用都 402 失败 → 代码按「抽取失败=什么都没说」处理（`backend/app/graph/nodes.py` 的 `parse_intent`，失败分支返回全 `missing_required`）→ 永远走 `ask_more` 追问。
3. 追问文案是模板（缺 destination/date 就问），用户看到的永远是"还差两项必填项"，**功能实际瘫痪**。

> 注意：`.env` 顶部注释写着"主链路 2026-09-16 起走百炼免费额度"，但实际 `LLM_BASE_URL=https://api.deepseek.com/v1`、`LLM_API_KEY` 是 DeepSeek key——**注释与配置不符**，主链路实际一直在走 DeepSeek 付费。这是本次误判的诱因，已在下面第二节修正配置时顺手对齐注释。

## 三、实测性能数据（2026-09-17）

| 项 | 结果 |
|---|---|
| 修复前 `parse_intent` | 每次 **402 失败** → 永远追问 |

## 七、待后端处理：`/assistant` 报「候选池是空的」（2026-09-17 用户实测）

**用户侧现象**：`/assistant` 发消息后，页面出现红框错误：

> 候选池是空的 —— 这一轮模型没有成功调用过 search_poi，无法在封闭世界内生成行程。

**错误来源**：`backend/app/graph/nodes.py` `generate_plan`（约 581 行）——工具循环结束时**候选池（POI 池）为空**时返回。

**根因面（已排查，两个方向）**：

1. **mock 模式限制（最可能）**：`.env` 目前 `AMAP_PROVIDER=mock`，`backend/app/providers/mock.py` 注释明确「mock 池里 9 个点**全在成都**，`search_poi(city=...)` 传**别的城市会得到空列表**」。**目的地不是成都时，子 agent 搜不到任何 POI → 候选池空 → 该报错**。
2. **模型工具调用偶发不稳**：主 agent 通过 `task` 子 agent 间接调 `search_poi`（主 agent 工具集只有 task/get_weather/calc_distance）。若某轮 `agent_step` 的模型（当前 `deepseek-v4-flash-0731`，百炼）没产出任何 `tool_call` 就收工，同样导致池空。

**复现实锤（2026-09-17，`deepseek-v4-flash-0731`，端到端 SSE 实测）**：
- 成都完整需求 → 8 次工具调用、行程正常生成 ✅（140s / 另一轮 214s，波动大）
- ✅ **非成都（杭州）已实测复现**（21:30）：**159.3s 后**收到
  `{"type":"error","code":"internal_error","msg":"候选池是空的 —— 这一轮模型没有成功调用过 search_poi，…"}`
  工具调用 **7 次全是 `task` 子代理**（+1 次 `get_weather`）、**0 次 `calc_distance`**（无 POI 可算）
  → **根因确认是 mock 数据源，不是模型空转**：`providers/mock.py:397`
  `if city and MOCK_CITY not in city: return []`（第 42 行注释已写明）

🔴 **两个衍生问题（比"池空"本身更值得修）**：

1. **文案是技术黑话直发用户**（"候选池" / "封闭世界" / "search_poi"）——
   演示时对方随便说个非成都城市就会看到这行红字。**这是产品缺陷，不是代码 bug**
2. **白等 159s** —— 子代理搜空后主 agent **反复派 `task`**（7 次 ≈ 100s 全是无效劳动），
   最后靠 L2 工具上限兜底才走到 `generate_plan`。**兜底生效了，但兜得太晚**

**修法候选（按代价排序）**：

| 方案 | 改哪 | 代价 |
|---|---|---|
| **A 改文案** | `nodes.py:578` 池空分支：按 `mock/real` + 目的地给**人话**（如"演示数据只覆盖成都，换成成都试试？"） | ⚠️ **不是一处**：这段文案被 **3 个测试断言**（`test_graph.py:599`、`test_graph.py:619`、`test_nodes.py:490`）→ 要同步改断言；且 `nodes.py` 目前**没 import `settings`**，拿 provider 得新增依赖 |
| **B 提前拦截**（最优体验） | `parse_intent` 拿到目的地后就判断，mock 不支持则**立刻**告知，不进工具循环 | 3~5 处；**省掉那 159s**（这才是这笔时间的真正去处：7 轮 `task` × 8 轮上限） |
| **C 扩 mock 池** | `providers/mock.py` 加第二批城市 | 数据活，量大 |
| **D 演示切 real** | `.env` `AMAP_PROVIDER=real` | 一行配置，但依赖现场网络 + 高德 key |

⚠️ **未拍板前不要动** —— 这不是"模型空转"，**换模型 / 调 prompt 都修不好它**（根因在数据源与文案）。

### ✅ 处置结果（2026-09-17 晚）—— 选了 D，并顺带修掉一个更严重的隐患

**决定走 D（切 real）**：这条路径本来就是"演示 / 真实使用"该走的档；
mock 档的价值（零 Key 可跑）完全不受影响 —— **两档并存，各司其职**。

**已改动三处**：

| # | 文件 | 改动 |
|---|---|---|
| 1 | `.env:40` | `AMAP_PROVIDER=mock` → **`real`**（`AMAP_WEBSERVICE_KEY` 早已配好，32 位） |
| 2 | `tests/test_mock_provider.py:60` | 原 `test_build_provider_defaults_to_mock` → `test_build_provider_follows_configured_provider`：断言从「写死是 mock」改成「**跟随全局配置**」。理由：测试不该跟本机配置绑死，否则**切档必红** —— 而这类红最难查（代码没坏，是环境变了） |
| 3 | `app/providers/amap.py` | 限速状态**实例级 → 模块级**（`_next_slot_ts`，取号式排队）。见下方 |

**真链路实测（`real` 档，4+ 次出站，总耗时 2.6s）**：

```
[search_poi 成都/武侯祠] 3 条 · 成都武侯祠博物馆 (104.047992,30.646168) open=08:30-18:30 rating=4.8
[search_poi 杭州/西湖]   3 条 · 杭州西湖风景名胜区 (120.121358,30.222692) open=24小时营业 rating=4.9
[calc_distance] 西湖 → 断桥残雪: 8.99 km / 24 min（直线 4.88 km）
[get_weather 杭州] status=ok，多云/晴，31/24℃
```

→ **非成都目的地搜空的问题在 `real` 档下不存在**（本节的根因只在 `mock` 档成立）。
→ 但**衍生问题 1（文案是技术黑话）依然存在**：`real` 档下"池空"虽罕见，
   真遇到限流 / 参数错时仍会走到那句红字。**A 方案（改文案）仍建议做**，只是紧迫性下降。

**🔴 顺带修掉一个更严重的隐患：限速在并发下失效**

排查本节问题时发现：`AmapHttpProvider` 的限速状态（原 `self._lock` / `self._last_call`）
是**实例级**的，而 provider 是**每请求新建**的（`api/chat_stream.py` 的 factory 每请求建图）。
→ **并发 N 个请求 = N 把互不知情的锁 = 出站 2.2N QPS**，**2 并发就踩到高德限流线**。
而 `CUQPS_*` 是 `status=0` + HTTP 200 + **不抛异常** → 会被上层当成"搜不到" → **触发假硬错白打回**。

**为什么一直没暴露**：mock 不联网，根本没有限速这回事 → **只有 `real` 档才会现形**。
换句话说，这个问题和"要不要切 real"是绑在一起的 —— **切之前必须一起修**。

**改法**：限速状态提到模块级，改**取号式排队**（同步取走自己那格的发车时刻，再异步等）。
取号两行之间没有 `await`，在单 event loop 内天然原子 → 不需要锁，也不碰 loop（跨 event loop 安全）。

**边界（诚实）**：这只解决**同进程**并发。**多 worker / 多实例**各自一份模块级状态，
仍需跨进程限速（Redis）—— **不做**（D28 已定"进程内滑动窗口，不引 Redis"；当前单进程部署够用）。
